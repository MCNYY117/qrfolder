# 安全设计

QRFolder 的设计目标是：**把一个目录只读地暴露到公网，且不做任何超出你明确授权的事**。
这份文档说明它防住了什么、怎么防的、以及**没防住什么**。

---

## 1. 威胁模型

### 假设存在

- 攻击者能发起任意 HTTP 请求，包括畸形路径、伪造请求头、超大请求体
- 攻击者知道或能猜到你部署了本服务（但未必知道后台路径）
- 内容目录里的文件名部分可控（例如允许用户上传文件到该目录）
- 反向代理的配置由你负责，QRFolder 无法验证它是否可信

### 假设不存在

- 攻击者已经拿到服务器上的任意代码执行权限（到这个地步已经无关本服务）
- 攻击者能物理接触服务器
- 内容目录本身是不可信的（**这一条是重要假设 —— 见第 6 节**）

### 明确的非目标

- **不是多租户系统。** 有多管理员（一个超级管理员 + 若干子管理员，见第 4 节），
  但那是**一个运维团队内部的分工**，不是给互不信任的客户做隔离：所有账号同属一个
  进程、一份配置、一个内容根，没有租户级配额、没有审计追踪、也没有「子管理员
  自己开子管理员」这种层级。真正要多租户，请一个租户跑一个实例。
- **不做内容加密。** 文件以明文经 HTTP 传输，靠外部 TLS 保护。
- **不做防病毒。** 上传什么就发什么（文件类型有一定的下载降级，见第 5 节）。

## 2. 路径穿越防护

这是整个项目风险最集中的地方 —— 一个疏忽就是任意文件读取。

### 关键结论（实测得出）

```
new URL('http://h/a/%2e%2e/%2e%2e/x').pathname  ->  "/x"
    ↑ %2e%2e 被 WHATWG URL 解析器免费归一化掉了

new URL('http://h/a%2f..%2fb').pathname         ->  "/a%2f..%2fb"
    ↑ %2f 原样穿过 URL 解析器

decodeURIComponent('/a%2f..%2fb')               ->  "/a/../b"
    ↑ 解码那一刻才凭空多出分隔符

new URL('http://h/a/..%5c..%5cb').pathname      ->  "/a/..%5c..%5cb"
decodeURIComponent('/a/..%5c..%5cb')            ->  "/a/..\..\b"
    ↑ Windows 上 \ 就是分隔符

path.win32.resolve('D:/root', 'C:/x')           ->  "C:\x"
    ↑ resolve 会丢掉 root
```

**因此核心规则是：必须先按 `/` 切分，再对每一段单独解码。**
反过来（先整体 `decodeURIComponent` 再切分）就是任意文件读取漏洞。
实现见 `src/serving/safePath.ts`，那里的注释也写着同一条规则。

### 五层防御

| 层 | 手段 | 挡住的攻击 |
|---|---|---|
| ① | `new URL()` 归一化 | `%2e%2e`、`./`、重复斜杠 |
| ② | 段级校验 | `%2f` / `%5c` 夹带分隔符、NUL 字节、盘符、NTFS 数据流、Windows 保留设备名、尾随点/空格 |
| ③ | `path.join` 而非 `path.resolve` | root 被绝对路径片段静默丢弃（Linux 不发作，只在 Windows 炸） |
| ④ | `isInside()` 包含性检查 | UNC 路径 `//server/share` |
| ⑤ | `fs.realpath` 后复查 | 符号链接 / NTFS junction 逃逸 |

### 两个容易写错的细节

**其一：`isInside` 不能写成 `rel.startsWith('..')`**

```ts
// 错误：目录里一个叫 "..foo" 的合法文件会被误杀
if (rel.startsWith('..')) return false;

// 正确
if (rel === '..') return false;
if (rel.startsWith('..' + path.sep)) return false;
return !path.isAbsolute(rel);
```

**其二：Windows 会静默剥掉路径段末尾的点和空格**

```ts
// ".. " 既躲过 seg === '..' 的字面比较，
// 又会被文件系统当成 ".." 解析 —— 一条完整的穿越路径
if (/[. ]$/.test(seg)) throw new UnsafePathError('trailing dot or space');
```

同理 `foo.` 与 `foo` 指向同一个文件，可用于绕过扩展名黑名单。

### 测试

`test/safePath.test.ts` 收录了 29 个用例，覆盖上述全部向量，外加合法路径的误杀回归测试（中文、空格、`..foo` 这类文件名）。

```bash
node --test test/safePath.test.ts
```

### 残留风险：TOCTOU

第 ⑤ 层与真正的 `open()` 之间存在时间窗口 —— 攻击者若能在校验通过后、打开之前把文件换成指向别处的链接，就能绕过。

**Node 没有可用的 `O_NOFOLLOW` 语义**（Windows 上尤其没有），无法彻底消除这个窗口。

缓解措施：内容目录应当**只由运维写入**。能做到这一点的话，风险就归结为"能写内容目录的人本来就能改内容"。真要更严，可以在打开后用 `fh.stat()` 复查 size/mtime 是否与校验时一致。

## 3. 认证与会话

### 密码存储

用 Node 内置的 `crypto.scrypt`，参数 N=16384, r=8, p=1, keylen=64。

三个实现上的坑，都在 `src/admin/auth.ts` 里处理了：

1. **绝不用 `scryptSync`。** 单次约 50~120ms 且占 16MiB 内存，同步版本会把事件循环卡死，几个人同时登录服务就假死。
2. **必须限制并发。** 攻击者并发 500 个登录请求 = 500 × 16MiB = 8GB 内存，直接 OOM。**按时间窗口的限流挡不住这个** —— 它允许突发并发。所以有一个独立的信号量（`maxConcurrentHashes`，默认 4），超出排队，队列也满则返回 503。
3. **密码先做 NFKC 归一化。** 中文/全角输入法下，同一个密码可能因 Unicode 表示不同而校验失败。

另外：未设置密码时也跑一次等价开销的哈希，让响应时间不可区分，避免攻击者靠计时判断"这个站点还没设密码"。

### 会话

无状态签名 cookie：`v2.<base64url(payload)>.<base64url(hmac-sha256)>`

- 不存服务端 —— 重启不掉线、不占内存、无并发清理问题
- 撤销手段是轮换 `sessionSecret`（后台有按钮，会明确提示"所有人将被登出"）
- 可选绑定来源 IP（`bindSessionToIp`，移动网络下会频繁掉线，默认关）

**票据里只有账号 id，没有角色、没有权限。** 角色和权限每次请求从内存配置里现查。
这么做是为了让「改了权限立刻生效」和「删了账号立刻失效」成立 —— 把权限写进票据，
改一次权限就得等 12 小时票据过期。

**版本号从 `v1` 升到 `v2`，是加账号体系这件事必需的一步。** 旧版本的校验函数会忽略
它不认识的字段，于是一张带账号 id 的 v1 票据会被旧代码当成普通管理员接受 ——
一旦回滚到旧版本，所有子管理员会被静默提升成超级管理员。版本号对不上，
旧代码对新票据一律返回 null。代价是升级时所有人重新登录一次。

**任何方法都读不到票据里的账号 id 时**（缺 `a` 字段的 admin 票据），一律拒绝 ——
放过去等于发了一张没有主体的通行证，调用方只能当超级管理员处理。

**一个必须注意的实现细节**：`timingSafeEqual` 在长度不等时会抛 `RangeError`。
不先比长度的话，攻击者发一个任意长度的伪造签名就能让服务器抛异常。

```ts
const expected = Buffer.from(sign(bodyB64, secret), 'utf8');
const given = Buffer.from(givenSig, 'utf8');
if (expected.length !== given.length) return null;   // ← 必须先比长度
if (!timingSafeEqual(expected, given)) return null;
```

### CSRF

两层：

1. 会话 cookie 用 `SameSite=Lax` —— 浏览器不会在跨站 POST 上携带它
2. 双提交令牌：由会话令牌派生 HMAC，随每个表单提交，服务端用 `timingSafeEqual` 比对

所有 POST 都校验，包括登出。缺失或错误返回 403。

### 登录限流

| 机制 | 挡什么 |
|---|---|
| 按 IP 失败计数 + 指数退避锁定 | 慢速在线爆破（15min → 30min → 60min …，上限可配） |
| scrypt 并发信号量 | 并发撞库打爆内存 |
| 失败时 200~500ms 随机延迟 | 进一步压低爆破速率 |
| 恒定失败文案 | 不回显"还剩几次"，不泄露账号是否存在 |

> 计数存内存，重启清零。单实例部署下这是可接受的；若要多实例，需要外部存储。

### 首次设置的保护

首次运行（配置文件里**还没有超级管理员账号**）时，设置页面**只允许从 `127.0.0.1` 访问**，
防止公网抢注。

判据是「有没有超级管理员账号」，不是「有没有设过密码」。顺带得到一个恢复路径：
超级管理员账号一旦没了（被误删、密码记录损坏），本机打开后台就会重新看到设置页。
这是单超级管理员模型的安全网。

## 4. 管理员账号与权限

### 两种角色

| 角色 | 看得见什么 |
|---|---|
| **超级管理员**（有且只有一个） | 全部目录、全部系统设置、全部后台页面 |
| **子管理员**（任意多个） | 只有自己创建的、或被分配给他的目录；只有被逐项勾选的功能 |

登录是**用户名 + 密码**。升级时老的 `adminPassword` 会被静默迁移成一个名为 `admin`
的超级管理员账号，密码不变。

### 两个正交的维度

只做其中一个都会漏：

- **能力**：账号级权限，13 项分 5 组（目录 / 文件 / 访问日志 / 外观 / 系统），逐项勾选
- **范围**：目录归属（每个目录有一个 `owner`）+ 授权父目录（子管理员只能在自己被授权的
  父目录下新建目录，不能手填任意服务器路径）

### 唯一执行点：fail-closed 的路由表

`src/admin/policy.ts` 里逐条列出每个后台路由：接受哪些方法、谁能走、碰哪个对象。
**没在表里的路由一律 404。** 在分发函数里新加一条 `if (sub === '/newthing')`，
在补上表项之前它是死代码 —— 于是「新加了后台路由却忘了配权限，结果对所有登录用户敞开」
这种事在结构上不可能发生。散落式的检查做不到这一点，它依赖每个人每次都记得写。

顺带修掉的一个既有问题：`/system/export` 以前**没有方法检查**，`POST` 一下就能拿到
整份配置（含密码哈希与会话密钥）。现在每个路由都要显式声明允许的方法。

### 拒绝一律 404

- **别人的目录** → 404。不确认这个目录存在。
- **没有这条路由的权限** → 404。不确认这个页面存在。
- **越出授权父目录** → 403，并且明说是这个原因。这一条例外是因为越界的是**请求本身**，
  不涉及「某个对象存不存在」。

内容面同理：子管理员在浏览器里直接输别人目录的网址，得到的是 404 ——
而且**排在目录密码分支之前**。走到密码分支就等于承认了这个目录存在。

### 子管理员拿不到什么

下面这些**不是勾选项**，写死为超级管理员专属：

- `/access/*`（含管理员自己的密码、IP 白名单、登录限流）—— 每一项都能用来提权
  或把站长自己锁在门外
- `/system/export`（含全部密码哈希与会话密钥）、`/system/import`（能整体替换配置 = 自己给自己提权）
- `/system/server`（含后台路径）、`/system/proxy`（开了 `trustProxy` 就能伪造来源 IP，
  等于绕过后台 IP 白名单）、`/system/parentroots`（它本身就是权限边界）
- `/system/log`、`/system/upload`（全局开关，影响所有管理员）、`/logs/clear`（抹掉痕迹）
- `/domain/*`（改的是公网 TLS 暴露面）、`/reload`、`/rotate-secret`（会把所有人踢下线，
  等于给了子管理员一个针对站长的拒绝服务按钮）
- `/users/*`（账号管理本身）

### 不能指向别人的地盘

子管理员新建或修改目录时，路径必须**既在自己的授权父目录里，又不落在别人名下的目录里**。

只查前一条是不够的，而且缺的这条能凑成一条完整的越权路径：

1. 授权父目录覆盖到了别人的目录 —— 「根目录 = 整个内容根」是最省事的配法，也是最常见的
2. 子管理员新建一个目录，路径填别人的那个目录
3. 新目录归他自己，所以归属检查、权限检查、内容面的 404 **全都放行**
4. 他从内容面把别人的文件读了出来

所以这条检查是必须的，不是锦上添花。唯一的例外：**路径没有改动时不查** ——
一个目录如果正好被摆在别人的目录之下（超级管理员安排的），改标题、改排序
不该因此被拒。超级管理员不受这条限制，他本来就看得见全部目录。

### 动作类权限会带上它的「查看」前置项

`dirs.create` / `dirs.update` / `dirs.delete` / `dirs.browse` / `dirs.qr` 会自动补上
`dirs.view`，`appearance.edit` 补 `appearance.view`，`logs.export` 补 `logs.view`。

不是为了方便，是为了消除一种**说得通但用不了**的状态：每个目录动作结束时都会
重定向回 `/admin/directories`，而那个页面要 `dirs.view` —— 只勾 `dirs.delete` 的话，
删除本身成功，然后浏览器落到一个 404，看着像"删坏了"。补齐在校验器里做，
**不产生 issue**（报 issue 会让 `store.reload()` 永远拒绝这份配置）。

### 界面收敛不等于强制

后台各页会按权限藏掉导航项和按钮，但那**只是省得人点了撞 404**。
强制始终在路由表里。侧边栏的可见项也是用**同一张策略表**算出来的，
不另写一份「权限 → 菜单」映射 —— 两份名单迟早漂移，漂移的方向一定是
「菜单里有、点进去 404」。

### 已知缺口

- **登录限流仍按 IP 计数，不按账号。** 分布式撞库打一个已知账号不会被限流。
  改成按账号又会给攻击者「锁死某个已知用户名」的手段，所以维持现状。
- **一个目录只能归一个管理员**，不支持多人共管。
- **只有一个超级管理员**，丢了密码靠本机首次设置页恢复。
- ~~两个子管理员的授权父目录重叠时，一个能把自己的目录指向另一个的地盘。~~
  **这条已经堵掉了**（见上面的「不能指向别人的地盘」）。剩下的运维责任只有一条：
  别把两个客户的资料放进同一个文件夹 —— 那样任何按目录的隔离都无从谈起。
- **`/system/export` 仍然导出密码哈希与会话密钥**（改成脱敏会破坏导入的往返一致性），
  只是现在只有超级管理员拿得到。

## 5. 后台暴露面

### 默认策略

`adminIpAllowlist` **默认为空（不限制）**。这是刻意的：开源项目要能开箱即用，硬性默认会让首次部署直接失败。

但后台会：

- **常驻显示你当前的 IP**，让你知道该往白名单里填什么
- 保存白名单时**校验你自己是否还在名单内**，不在则要求二次确认（防自锁）
- 在文档里推荐 `127.0.0.1/32` + SSH 隧道 / VPN 的组合

### 减少噪音

扫描器会不停地请求 `/admin`、`/wp-admin`、`/.env` 之类的路径。把后台路径改成 `adminPath` 里一个难猜的值，能让这些请求变成普通的 404。

### 未授权一律 404

内容面对"文件不存在"和"没有权限"返回**同一个 404**，不做区分。
后台路径不匹配时也返回 404，不确认后台是否存在。后台里"没这条路由的权限"
和"这个目录不归你"同样都是 404（见第 4 节）。

403 只有两处：**CSRF 校验失败**（那时请求方已经持有一个有效会话，
不存在信息泄露），以及**请求的路径越出了你的授权父目录**（越界的是请求本身，
不是某个对象的存在与否）。

## 6. 内容目录里的 HTML/SVG —— 被低估的风险

这是"信息发布服务"特有的问题，值得单独说。

**内容目录里的 `.html` / `.svg` 文件，浏览器会以你自己的源（origin）为上下文解析执行。**
而 `/admin` 在同一个源上，会话 cookie 是 `SameSite=Lax`，同源脚本可以发同源请求 —— **CSRF 令牌也就一起拿到了**。

等于说：如果你（或某个能往内容目录写文件的人）放进去一个恶意 HTML，它就能操作你的后台。

### 缓解

1. 这些扩展名一律**强制下载**（`Content-Disposition: attachment` + `Content-Type: application/octet-stream`）：
   `.html .htm .xhtml .shtml .svg .svgz .xml .xsl .xslt .js .mjs .cjs`
2. **所有响应都带 `X-Content-Type-Options: nosniff`** —— 没有它，浏览器可能无视你给的 `application/octet-stream` 去嗅探成 HTML
3. 未知扩展名同样强制下载，绝不让浏览器去猜

### 更彻底的做法

**把内容面放到独立子域名**（如 `files.example.com` 放内容、`admin.example.com` 放后台），
与后台不同源，这是唯一的根治方案。需要后台与内容分域部署。

## 7. 响应头

所有响应（含错误响应）都经过同一个入口下发：

```
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY | SAMEORIGIN
Content-Security-Policy: default-src 'none'; img-src 'self' data:;
    style-src 'nonce-…'; script-src 'nonce-…'; base-uri 'none';
    form-action 'self'; frame-ancestors …; object-src 'none'
Permissions-Policy: geolocation=(), camera=(), microphone=()
Cross-Origin-Resource-Policy: same-origin
Strict-Transport-Security: max-age=31536000   (仅 HTTPS)
```

- 内容页 `frame-ancestors 'self'`（允许自站 iframe 预览），后台 `'none'`
- **`Server` 与 `X-Powered-By` 完全不发** —— Node 的 http 模块默认就不发这两个头，只要不手动加就是干净的
- **CSP nonce 每次响应重新生成**。若在进程启动时生成一次并复用，等于没有 CSP —— 攻击者读一次页面就知道了

> ⚠️ **接入反向代理后必须复验。** Caddy 会给**它自己**产生的响应（错误页、重定向、静态响应）
> 加上 `Server: Caddy`，必须在站点级删掉 —— 注意是 `header -Server`，
> **不是** `header_down -Server`（后者只在 `reverse_proxy` 块内部合法，而且代理过来的响应本来就不带这个头）。
> 三处都要写：站点块、`handle_errors`、显式的 `:80` 块。完整配置见
> [deployment.zh-CN.md](deployment.zh-CN.md)。
>
> 验证时**三条路径都要试**，错误页和 80 端口最容易漏：
> ```bash
> for u in https://你的域名/ https://你的域名/不存在的路径 http://你的域名/; do
>   echo "== $u"; curl -sI "$u" | grep -i '^server:' || echo "   无 Server 头 ✅"
> done
> ```

## 8. 配置层面的防护

### 内容目录不得与受保护路径重叠

启动时与每次保存配置时都会校验：内容目录不能是盘符根、不能是应用目录、不能是配置文件所在目录，**也不能是它们的祖先**。

否则一次误配就会把含 `sessionSecret` 与密码哈希的 `config.json` 发布到公网。

> 这个校验曾经写错过一次：重叠检测的方向搞反了，导致任何位于受保护目录之外的**正常**内容目录都被判定为重叠并被丢弃。现在有回归测试锁住（`test/validate.test.ts`）。

### 配置值不能直接拼进 HTML

`accentColor` 这类配置值在插入 `<style>` 前会经 `/^#[0-9a-f]{6}$/i` 白名单校验。
否则一个手滑或恶意的配置值（如 `#fff}</style><script>…`）就是一条从配置面通往 XSS 的通路 —— 而后台会话 cookie 就在同源。

### 配置改坏时保留旧配置

配置文件解析失败或校验不通过时，服务**保留上一份有效配置并继续运行**，绝不降级为默认值。

理由：默认值是 `siteMode: "public"`。如果降级，一次手滑就可能把整站从"需密码"变成"公开"。

## 9. 已知限制

| 限制 | 说明 |
|---|---|
| TOCTOU 窗口 | 见第 2 节末尾。内容目录应只由运维写入 |
| 限流计数存内存 | 重启清零。多实例部署需要外部存储 |
| 管理员的隔离是"分工"不是"多租户" | 一个超级管理员 + 若干子管理员；同进程、同配置、同内容根。见第 1 节与第 4 节 |
| 登录限流按 IP 不按账号 | 分布式撞库打一个已知账号不受限。见第 4 节末尾的取舍说明 |
| GBK 文本乱码 | Node 只认 UTF-8 文本，建议转码 |
| 后台与内容同源 | 见第 6 节，分域部署可根治 |
| 无内置 TLS | 设计如此 —— 交给 Caddy/nginx，它们做得更好 |
